# Bridge 1.1.0

Draft for release review.

## What changed

- **Delivery tells you what happened.** Send results distinguish a confirmed transport handoff, a confirmed no-write failure, and an unknown result, with a recovery step for each. Repeat a confirmed no-write failure only as directed, using the same ID and text. For an uncertain attempt, check the recipient and outgoing records before sending again. `submitted` still means a transport write; it does not guarantee the recipient read or accepted the message. Peer notices separate verified sender identity from the quoted text.
- **Discovery is more useful when part of a route is down.** A stale Codex Desktop record no longer hides another usable one. When a Claude conversation is open twice, the bridge chooses a reachable window by status activity. Spare and parked Claude processes and unusable daemon rows are omitted instead of looking sendable. A partially checked catalog can warn without losing the results it found. Transport errors and doctor checks give bridge-owned causes instead of raw upstream diagnostics.
- **Local delivery records stay in place.** The bridge no longer moves old state online. Reads can continue while a send waits for a ledger lock, and paged history can report a gap rather than silently skipping it. Existing receipts are retained; the [offline migration and rollback guidance](../../README.md#updating-from-a-version-before-100) matters if more than one state location exists.
- **The conversation panel handles interrupted sends better.** It keeps edits made during a send, shows the Claude handoff and the copy to your Codex chat separately, and names both destinations before sending. **Check again** reads history only; it never resubmits the draft. If Codex does not report its Enter setting, Enter adds a line and Ctrl+Enter or Cmd+Enter sends. Saved conversation titles and project folders are in widget metadata instead of the model-visible launcher result.
- **Installing no longer creates a second Claude project server in the source checkout.** Claude MCP configuration belongs to the plugin. Local settings stay out of release packages, and the installer preserves unidentified directories and unmarked backups.

- **Shorter send receipts are opt-in.** `include_message: false` omits only your own text from a public send receipt. Old calls still receive the message, and ledger and panel records still include it. To check an unclear handoff once, use `list_deliveries` with its `message_id` and match the exact route. An absent record does not establish whether the message went out; no native read receipt is implied.
- **Replies and troubleshooting:** use the verified conversation ID, not an incoming message ID. Windows terminal senders carry a terminal reply hint; a cross-host return path must be verified independently. Doctor can identify one observed blocker and its next action without prescribing repairs for unused routes.

## Compatibility and updating

- **Route changes:** Windows Codex Desktop sends are local only; a Desktop app without a host-aware send tool is not used. On macOS, Codex requires an explicit SSH alias and never falls back locally. Only loaded idle SSH targets are listed. SSH connection sharing is disabled. The merged SSH route is covered by simulated transport tests, not a new live smoke test.
- **If panel and server versions differ:** a cached 1.0.6 panel can still work with a 1.1 server but lists live conversations only. The new panel reads the full saved catalog from the new server's widget metadata; with a 1.0.6 server it can read the catalog from the legacy result, without the new server's privacy boundary. The mixed versions were checked with host fixtures, not both native client combinations.
- **Update both clients:** use the [installation and reload steps](../../README.md#installation), then check that each client is running the updated server. Restart non-interactive and desktop sessions as documented. A 1.0.6 server running from an unchanged client cache cannot see a newer install in a different folder: no warning there is not proof that it updated. Existing saved receipts are not a reason to resend anything after an update.
